================================================================================
🏛️ THE ENTERPRISE SOFTWARE ARCHITECTURE SCALING BLUEPRINT & PLAYBOOK
================================================================================
This file serves as a comprehensive reference guide for developers and architects
designing backends at various business scales using Python/FastAPI.

Each scale defines:
1. Architectural Blueprint & Directory Layout
2. Technology Stack (Database, Caching, Background Workers)
3. Infrastructure & DevOps (Docker, CI/CD, Logging)
4. Domain examples (Jira, HRMS, API Monitor)

================================================================================
1. 🧪 SMALL-SCALE ARCHITECTURE: THE PRAGMATIC CRUD / FLAT LAYOUT
================================================================================
Best suited for:
* Proofs of Concept (POC), Internal Hackathons, or tiny utility microservices.
* Examples: API Uptime Monitor, Slack Notification Webhook, simple URL Shortener.
* Team Size: 1-2 Developers.

--------------------------------------------------------------------------------
1.1 Directory Structure
--------------------------------------------------------------------------------
Keep the codebase flat to maximize delivery speed. No abstract interfaces.

api_monitor/
├── app/
│   ├── database.py         # SQLAlchemy Engine & SQLite/Postgres connect
│   ├── main.py             # Single file for all routes & business logic
│   ├── models.py           # SQLite tables
│   └── schemas.py          # Pydantic input/output schemas
├── Dockerfile
├── docker-compose.yml
├── .github/
│   └── workflows/
│       └── ci.yml
└── requirements.txt

--------------------------------------------------------------------------------
1.2 Technology & Caching Stack
--------------------------------------------------------------------------------
* Database: **SQLite** (In-memory/local file) or **PostgreSQL (Single Instance)**.
* Caching: None, or in-memory dicts.
* Background Processing: Simple **FastAPI BackgroundTasks** (runs in-process).

--------------------------------------------------------------------------------
1.3 Docker & CI/CD Setup
--------------------------------------------------------------------------------
* Docker: Simple single-stage Dockerfile.
* CI/CD: Simple GitHub Actions checking format (ruff/black) and running pytest.

--- DOCKERFILE SKELETON ---
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY ./app ./app
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

--- CI/CD GITHUB ACTIONS SKELETON ---
name: Small Scale CI
on: [push, pull_request]
jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: "3.11"
      - name: Install dependencies
        run: |
          pip install ruff pytest
          pip install -r requirements.txt
      - name: Lint with Ruff
        run: ruff check app/
      - name: Run Tests
        run: pytest


================================================================================
2. 🚀 MEDIUM-SCALE ARCHITECTURE: THE LAYERED / MONOLITHIC SYSTEM
================================================================================
Best suited for:
* Standard SaaS platforms, single-tenant products, or internal business apps.
* Examples: Simple E-Commerce, Blog platform, Booking Management portal.
* Team Size: 3-8 Developers.

--------------------------------------------------------------------------------
2.1 Directory Structure
--------------------------------------------------------------------------------
Organized by technical layers. Separates data models from business handlers.

app/
├── api/
│   ├── endpoints/
│   │   ├── users.py
│   │   └── bookings.py
│   └── deps.py             # Shared DB dependencies
├── core/
│   └── config.py
├── models/                 # SQLAlchemy tables
│   ├── users.py
│   └── bookings.py
├── schemas/                # Pydantic validation
│   ├── users.py
│   └── bookings.py
├── services/               # Flat Service logic (No interfaces)
│   ├── user_service.py
│   └── booking_service.py
├── Dockerfile
├── docker-compose.yml
└── requirements.txt

--------------------------------------------------------------------------------
2.2 Technology & Caching Stack
--------------------------------------------------------------------------------
* Database: **PostgreSQL (Standalone Instance)**.
* Caching: **Redis (Single Node)** for endpoint caching (e.g. `fastapi-cache`).
* Background Workers: Simple **Celery** worker running on Redis as a broker.

--- DOCKER COMPOSE SKELETON ---
version: '3.8'
services:
  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB: saas_db
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: password
    ports:
      - "5432:5432"

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"

  web:
    build: .
    command: uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql+asyncpg://postgres:password@db:5432/saas_db
      - REDIS_URL=redis://redis:6379/0
    depends_on:
      - db
      - redis


================================================================================
3. 🏢 LARGE/ENTERPRISE ARCHITECTURE: THE DOMAIN-DRIVEN SEMI-MODULAR MONOLITH
================================================================================
Best suited for:
* Large, highly complex enterprise operations with multiple modules and side effects.
* Examples: Jira, HRMS (incorporating Employees, Leave, Attendance, Tasks, Projects,
  Holidays, Announcements, Roles/Permissions).
* Team Size: 10+ Developers (split into cross-functional feature streams).

--------------------------------------------------------------------------------
3.1 Directory Structure
--------------------------------------------------------------------------------
Centralized Data Models & Validation to prevent Python circular runtime imports, 
combined with deeply decoupled feature-folders containing abstract interface boundaries.

app/
├── core/                        # Security, global configs, JWT authentication
├── database/                    # Connection pools, migration settings
│   ├── sessions.py              # async_sessionmaker & get_db helper
│   └── base.py                  # Declarative SQLAlchemy base
│
├── models/                      # CENTRALIZED ORM TABLES (Crucial for Python)
│   ├── users.py                 # User & Role tables
│   ├── leave.py                 # Leave tables (Foreign key to User)
│   └── projects.py              # Project & Task tables
│
├── schema/                      # CENTRALIZED VALIDATION SCHEMAS
│   ├── users.py
│   └── leave.py
│
├── shared/                      # Shared abstract helpers, utils, exception handlers
│   ├── base_repo.py             # Abstract Base Repo
│   ├── base_service.py          # Abstract Generic Base Service
│   └── utils/
│       └── security.py          # Password hashing utilities
│
└── modules/                     # FEATURE DOMAIN LAYERS (Zero Layer Cross-Talk)
    ├── users/
    │   ├── interfaces/
    │   │   ├── user_repo_interface.py     # IUserRepo Interface
    │   │   └── user_service_interface.py  # IUserService Interface
    │   ├── repos.py             # UserRepo implementing IUserRepo
    │   ├── services.py          # UserService implementing IUserService
    │   ├── dependencies.py      # Dependency provider mapping Interface -> Concrete
    │   └── router.py            # API Route definitions
    │
    └── leave/
        ├── interfaces/
        │   ├── leave_repo_interface.py
        │   └── leave_service_interface.py
        ├── repos.py             # LeaveRepo
        ├── services.py          # LeaveService (Calls users/services.py via DI for logic)
        ├── dependencies.py
        └── router.py

--------------------------------------------------------------------------------
3.2 Technology, Caching & Message Queue Stack
--------------------------------------------------------------------------------
* Primary Database: **PostgreSQL (Highly Available Cluster)**
  - Read/Write replica split.
  - TimescaleDB extension for time-series data (e.g. Employee Clock-In sheets).
* Caching Layer: **Redis Cluster**
  - **Read Cache**: For user profiles, session states, announcements (expiration TTL enabled).
  - **Rate Limiting**: Custom middleware using Redis Token Bucket to limit API thrashing.
* Background Workers: **Celery + RabbitMQ (Broker)**
  - Heavy tasks (dispatching leave approval emails, calculating monthly payroll sheets,
    syncing Jira dashboard items) are offloaded to Celery.
  - Broker: **RabbitMQ** (guarantees delivery and offers advanced route grouping).

--- ENTERPRISE SERVICE BUS (CELERY) SETUP ---
# app/core/celery_app.py
from celery import Celery
from app.core.config import config

celery_app = Celery(
    "hrms_tasks",
    broker=config.RABBITMQ_URL,
    backend=config.REDIS_URL,
    include=["app.modules.leave.tasks", "app.modules.users.tasks"]
)

# Enterprise configuration
celery_app.conf.update(
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],
    timezone="UTC",
    enable_utc=True,
    task_acks_late=True,             # Tasks acknowledged only AFTER successful completion
    worker_prefetch_multiplier=1,    # Fair distribution of heavy HRMS tasks
)

--------------------------------------------------------------------------------
3.3 Infrastructure & Enterprise CI/CD Pipeline
--------------------------------------------------------------------------------
* Containerization: Multi-stage production Dockerfile utilizing alpine/slim to
  minimize security vulnerability footprints (CVEs) and image sizes.
* CI/CD: Automated linting, static type analysis (mypy), security scanning (bandit),
  unit testing with mock injection, building the Docker image, pushing to Amazon ECR,
  and executing a rolling upgrade to Amazon ECS or Kubernetes (EKS).

--- MULTI-STAGE ENTERPRISE DOCKERFILE ---
# Stage 1: Build virtual environment dependencies
FROM python:3.11-slim AS builder
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends gcc build-essential libpq-dev
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Stage 2: Final minimal runtime stage
FROM python:3.11-slim AS runner
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends libpq5 && rm -rf /var/lib/apt/lists/*
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

--- ENTERPRISE GITHUB ACTIONS PIPELINE (.github/workflows/ci-cd.yml) ---
name: Enterprise HRMS Pipeline

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  quality-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: "3.11"
          
      - name: Install Linting & Testing Tools
        run: |
          pip install ruff mypy bandit pytest pytest-cov pytest-asyncio
          pip install -r requirements.txt
          
      - name: Quality Gate 1: Code Formatting
        run: ruff format --check app/
        
      - name: Quality Gate 2: Static Type Analysis
        run: mypy app/
        
      - name: Quality Gate 3: Security vulnerability scanning
        run: bandit -r app/ -x tests/
        
      - name: Quality Gate 4: Test Suite with coverage verification
        run: pytest --cov=app --cov-fail-under=90 tests/

  build-and-deploy:
    needs: quality-gate
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: us-east-1
          
      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v1
        
      - name: Build, Tag, and Push Docker Image to ECR
        env:
          ECR_REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          ECR_REPOSITORY: hrms-backend
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG .
          docker push $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG
          
      - name: Deploy Rolling Update to ECS
        run: |
          aws ecs update-service --cluster hrms-prod-cluster --service hrms-web-service --force-new-deployment
